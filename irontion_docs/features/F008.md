# F008: Reminders

A reminder tells the user about a note at a time they chose. It is **its own feature**, not part of the Calendar ([[F007]]): the Calendar answers "which day is this note on?", a reminder answers "when should I be told?". Any note ([[F006]]) can have one reminder.

> [!info] Overview
> - Set it on a note's paper: the **Remind me** tool opens a dialog with quick times or a day and a time
> - A **Reminders** page (sidebar item) lists notes that have one: **Upcoming** and **Past**
> - A reminder can also open a **popup window** (Settings → Notes → Notifications → **Show reminders in a popup window**, off by default): a small window styled like a retro alert, in the app's theme, that appears even when the main window is hidden. Either, both or neither of the system notification and the popup can be on
> - Irontion **asks once**, the first time a reminder is set: "Allow notifications?". **Allowed**: a reminder is a **system notification** only. **Not allowed** (or not answered yet): it is a **notice** in the window that stays until dismissed, with **Open note** (unless the popup window showed it). Each reminder is delivered **once**
> - The **Rust side** checks, so it does not depend on the window being visible. It runs **while Irontion is running**; it cannot notify when the app is closed (see Open Questions)
> - Reminders missed while the app was closed or the machine asleep are shown at the next start (same day only), worded as **missed**
> - **Settings → Notes → Notifications** has the switch **Show reminders as system notifications**, shows whether the system can notify, and has a **Send test notification** button
> - Times are stored in **UTC** and shown in local time, in the user's date and 12/24-hour format ([[F003]])

## Setting a Reminder

| Choice | Time |
| ------ | ---- |
| In 1 hour | One hour from now, seconds dropped |
| Tomorrow morning | Tomorrow at 09:00 local |
| Next Monday morning | The coming Monday at 09:00 local (a full week away on a Monday) |
| Day and time | The shared date picker and the shared **time picker** (both dialogs; see below). **Set reminder** is disabled for a time in the past, with no hint text |

- Choosing a time sets it at once. **Remove reminder** clears it.
- The Remind me button shows the time when one is set; a card shows a bell chip with the time (accent color while upcoming, muted once past).
- Setting a reminder again makes it **due again**, even if the earlier one was shown.
- Setting or clearing a reminder is **not an edit**: the note's `updated_at` stays.
- On a note not written yet, the reminder is applied when the note is created.

## The Time Picker

The time button shows the time as the user's clock does ("09:00 AM", or "09:00" on a 24-hour clock). It opens a **clock** (`components/TimePicker.svelte`), the same on every page that picks a time of day:

- A large **hour : minute** header (with an **AM / PM** stack on a 12-hour clock). The hour is chosen first on the round dial; letting go moves on to the **minutes** (tap the header to go back). **OK** keeps the time, **Cancel** or Esc leaves it as it was.
- The dial: tap or drag. A 12-hour dial has 1-12 (12 on top); a 24-hour dial adds an inner ring of 00 and 13-23. Minutes are chosen to the minute, with a number printed every 5.
- Keys: arrow keys step the focused dial, Enter goes on to the minutes. The **keyboard** button swaps the dial for two typed fields (a red border and a disabled OK for a time that is not real).
- Follows **Settings → Language and region** (12 or 24-hour); AM and PM are named by the language. Works from 390px, both themes.
- Logic: `domain/clockDial.ts` (marks, angle and ring to value, hand, 12-hour conversion), unit-tested; the face is `components/ClockDial.svelte`.

## The Popup Window

A due reminder can open a small window of its own, a third way to be told, with its own switch (**Show reminders in a popup window**, Settings → Notes → Notifications, off by default) and a **Preview** button beside it that opens a sample.

| Part | Behavior |
| ---- | -------- |
| Window | 460 x 280, borderless, centered, in front of other windows, not resizable. Opened by Rust (`reminders::show_alert_window`), so it appears even when the main window is hidden or minimized. One per note: delivering again brings the open one forward |
| Look | A reference sketch of a retro alert, in **our theme**: a title bar in the accent color ("Reminder", or "Missed reminder") that drags the window, a round close button, a warning icon, **Remember!** and the note's text, then a chunky **OK**. Borders use the text color, the body the accent's soft tint; it follows light, dark and the user's accent and language |
| OK, the close button, Esc | Close the popup. OK has focus, so Enter works |
| Open note | Only when the note still exists: brings the main window forward on that note (`open_note_from_alert`), then closes the popup |
| Note deleted since | The popup closes at once: nothing to announce |
| Counts as shown | A popup that opened means the in-app notice is not shown too. If it fails to open (logged), the notice still appears |
| Page | `/alert?note=<id>&missed=0|1` (or `?sample=1`): a bare page with no sidebar and no app logic; the root layout skips `AppShell` for `/alert`, so only the main window runs the reminder watcher |
| Window permissions | `capabilities/default.json` covers `alert-*` windows, with `core:window:allow-start-dragging` for the title bar |

Limits: Wayland compositors (GNOME) may ignore "always on top" and may show "Irontion is ready" instead of raising a window opened from the background; the window is still created and in the taskbar.

## Asking Permission

| When | What happens |
| ---- | ------------ |
| The first reminder is set (from the Remind me dialog, on a new or existing note) and the user has never answered | The dialog **Allow notifications?** with **Allow notifications** and **Don't allow** |
| Allow | Saved as `allowed`. Reminders are system notifications only |
| Don't allow | Saved as `denied`. Reminders are in-app notices. Not asked again |
| Closed without an answer (×, Esc) | Nothing saved; asked again with the next reminder. Until then reminders are in-app notices |
| Settings → Notes → Notifications | The switch **Show reminders as system notifications** changes the answer at any time |
| Turning it on (the switch, or **Allow notifications** in the dialog) | Irontion **checks that the system really shows a notification**: it sends one ("Reminders: This is how a reminder looks.") and only if that works saves `allowed`. The first time on macOS, the system's own permission prompt appears here. If the system has no notification service, blocks Irontion, or the user refuses its prompt, the switch **turns itself back off**, a notice says why, and the answer is saved as `denied` |
| Turning it off | Saved as `denied`; reminders are in-app notices again |

The answer lives in the database (`settings` table, key `notifications`), not in the window, because Rust decides at delivery time, even before the window has loaded. Linux has no permission prompt for desktop apps, so this is Irontion's own question; GNOME's per-app settings (Settings → Notifications → Irontion) still apply on top.

## When It Is Due

- A **background thread in Rust** (`src-tauri/src/reminders.rs`) checks **every 20 seconds**, 3 seconds after start and then on. It does not use the webview, so a hidden, minimized or throttled window cannot make a reminder late.
- A reminder is due when `remind_at` is at or before now and `reminded_at` is empty. `remind_at` is an **instant** (UTC), so the user's time zone cannot move it to another day: 06:00 in Bangkok is 23:00 UTC the day before, and it fires at 06:00 Bangkok on the note's reminder day.
- Delivery: if the user allowed it (`settings::notification_permission` is `allowed`), the system notification (title "Reminder", the note's text as the body); an event to the window, which shows a sticky notice "Reminder: <text>" with **Open note** **only when the system notification was not shown** (not allowed, not answered yet, or it failed: `Delivery.shown`); and `reminded_at` is recorded. So a reminder is delivered once and never comes back unless the user sets it again.

- **Catch-up:** a reminder that came due while the app was closed or the machine asleep is delivered at the next check after launch if it is **today's** (local day), titled **Missed reminder** (or, when not allowed, a notice "Missed reminder: <text>"). A reminder from an **earlier day** is only marked delivered (it stays in the Past list), so opening the app after a week does not show a pile. "On time" means within 2 minutes of its time.
- **If the system notification fails** (no notification service, for example), the reminder is still marked delivered, the window shows the reminder itself, and a notice says **why** it could not be shown. Nothing fails silently.
- Setting up: the window sends the notification's words in the user's language to Rust (`set_notification_texts`).
- Checks run in one thread, one after the other, so they never overlap.

## The Reminders Page

| Part | Behavior |
| ---- | -------- |
| Upcoming | Soonest first |
| Past | Most recent first. These were shown or are overdue; the user clears them when done |
| Each item | The note on paper (opens its paper) and **Clear reminder** below it |

The sidebar and drawer list **Reminders** after Notes. On a phone it is under **More** ([[F004]]).

## Rules (enforced in Rust)

| Rule | Error kind |
| ---- | ---------- |
| `remind_at` is UTC, `YYYY-MM-DDTHH:MM:SS` with optional milliseconds and a trailing `Z`; real date, hour 0-23, minute and second 0-59 | `invalidReminder` |
| The note must exist | `notFound` |
| It is stored in one shape (`...SS.fffZ`) so times compare correctly as text | |

A time in the past is accepted by the core (the UI refuses it); it simply becomes due.

## Decisions

| Decision | Why |
| -------- | --- |
| Reminders are a feature apart from the Calendar | The user asked for it: the Calendar is a day view of notes; a reminder is a moment in time |
| One reminder per note, stored on the note (`remind_at`, `reminded_at`) | Simple, and enough for sticky notes. No extra table |
| Polling every 30 seconds in the app | There is no background service. 30 seconds is precise enough for a sticky note and costs almost nothing (one indexed query) |
| The backend decides what is due (`due_reminders`) and records that it was shown | One source of truth; a restart doesn't show an old reminder again |
| The notice is **sticky** | A reminder that fades after 4 seconds is easy to miss |
| **Rust delivers**, not the window (was: a 30-second timer in the webview, in-app notice only) | A webview timer is throttled or suspended when the window is hidden or the machine sleeps, and an in-app notice was the only output, so a 06:00 reminder showed nothing at all ([[B002-reminders-never-fired]]) |
| `notify-rust` directly, not `tauri-plugin-notification` | The plugin's desktop `show()` runs the send on a task and **discards its result**, so a failure could never be reported. `notify-rust` returns the error, which we show |
| ~~The system notification and the in-app notice both appear when the window is open~~ → **one or the other** | The user found the second popup redundant (2026-10-08). The notice now appears only when the system notification was not shown |
| Ask before the first system notification, in the app | The user asked for it. Desktop Linux has no permission prompt, so it is Irontion's own question, stored in the database for Rust |
| Not answered yet means in-app only | No system notification without a yes |
| The popup is its own setting, not a mode of the notification switch (`settings` key `reminder_window`) | The user asked for it as an extra ("if I want"); it needs no system permission, and any mix of the two can be on |
| The popup is a real window opened from Rust, loading a bare `/alert` page | It must show with the main window hidden, which an in-app dialog cannot. The page holds no app logic, so the reminder watcher never runs twice |
| The popup gets the note by id and reads it from the database like any page | No note text travels in a URL |
| A yes is saved only after a notification was really sent (`reminders::enable_with`) | The user asked: if the system cannot or will not notify, the switch must not stay on. Linux and Windows have no permission prompt, so the only honest test is to send one |
| A failed send still marks the reminder delivered | Retrying every 20 seconds would flood the user with notices. The in-app notice keeps the text and says why; the reminder stays in the Past list |
| Catch-up shows **today's** missed reminders only | A week-old reminder is noise. Older ones are marked delivered and stay in Past |
| The system's notification availability is checked, not a system permission | Desktop apps need none. On Linux the status asks the notification service on D-Bus (`get_server_information`); an error there is shown with its reason |
| The "due" decision takes `now` as an argument (`due_reminders_at`, `plan`) | So tests can use any moment and time zone (Bangkok is tested) without waiting |
| Local time in the UI, UTC in storage | Time zones and clock changes don't corrupt stored reminders |

## Implementation

- Migration `crates/irontion-core/migrations/007_notes_board.sql` (`remind_at`, `reminded_at`, index `notes_remind`)
- Rules: `crates/irontion-core/src/notes.rs` (`set_reminder`, `due_reminders_at(conn, now)`, `mark_reminded`) and `validate::timestamp`, unit-tested
- Delivery: `apps/desktop/src-tauri/src/reminders.rs` (the thread, `plan`, `classify`, `local_day_start`, `show_notification`, `availability`), started from `lib.rs`; unit-tested
- Popup: `reminders::show_alert_window` (Rust), `routes/alert/+page.svelte`, `lib/components/AppShell.svelte` (what only the main window runs), `settings::reminder_window` in core; the window listens to nothing, the main window listens to `open-note`
- Permission: migration `crates/irontion-core/migrations/008_settings.sql`, `crates/irontion-core/src/settings.rs` (`notification_permission`, `set_notification_permission`), unit-tested; the dialog is `components/notes/NotificationAskModal.svelte`, opened by `reminders.askIfUndecided()` from the note paper
- Commands: `set_note_reminder`, `notification_status`, `send_test_notification`, `set_notification_texts`, `notification_permission`, `set_notification_permission`, `enable_notifications`, `reminder_window`, `set_reminder_window`, `preview_reminder_alert`, `dismiss_alert`, `open_note_from_alert` in `commands.rs`; the window listens to the `reminder-delivered` event (`Backend.watchReminders`, both backends in `apps/desktop/src/lib/api/`)
- Pure logic: `apps/desktop/src/lib/domain/reminders.ts` (quick times, local and UTC, split into upcoming and past), unit-tested
- Window side: `apps/desktop/src/lib/stores/reminders.svelte.ts` (turns a delivery into a sticky notice), started in `routes/+layout.svelte`; `components/settings/NotificationsPanel.svelte`
- UI: `components/notes/ReminderPicker.svelte`, `routes/reminders/+page.svelte`

## Open Questions

- **Tray icon:** should Irontion keep running in the tray when the window is closed, so reminders still arrive? (Not built: notifications cannot fire when the app is not running.)
- **Autostart:** start Irontion when the user logs in?
- **Background service:** a tiny separate process that only delivers reminders, even when the app is closed?
- Should the notification have an **Open note** action (click to open)? Needs the notification service's actions on each system.
- Should a past reminder be cleared automatically after the user opens the note?
